# Isolated Supabase RLS integration-test plan

Historical baseline: **no database, user, or policy tests executed in Milestone 0.1**. Milestone 1 adds `tests/integration/student-identity.mjs`; see its execution results in the milestone report. Existing `tests/rls/policies.sql` contains ten structural pgTAP assertions, not actual per-user allow/deny coverage. Historical migrations remain unchanged. The additive `202610120001_student_identity.sql` migration implements the identity authorization changes.

## Isolation and setup

1. Use a disposable local Supabase instance or an explicitly designated non-production project. Record its identifier and reject any production URL/reference before provisioning, migration, reset, or cleanup. Never use production students or credentials.
2. For local testing, use a scratch copy with Supabase CLI configuration and Docker. The repository currently has no `supabase/config.toml`; initialize configuration in the scratch environment, copy the existing migrations/seed unchanged, and run local `supabase start` and `supabase db reset --local` there. Resolve migration/seed failures before policy testing.
3. Apply all migrations in order, including author-column grant hardening and dashboard-role retirement. Provision verified students A and B, unverified student U, and optional moderator M/content creator C/programme manager P via a test-only setup process. Create profile rows explicitly if no signup trigger exists. Record actual grants and role assignments.
4. Use the privileged setup connection only to seed fixtures, verify unchanged rows, assign approved test roles, and clean up. Every assertion must use the anonymous client or the named user's JWT through PostgREST. Service-role tests bypass RLS and cannot count as authorization evidence.
5. For unverified-user database semantics that cannot be reached through confirmation-enabled login, use a separate SQL transaction with `SET LOCAL ROLE authenticated` and `set_config('request.jwt.claims', ..., true)` for U's UUID. Clearly label simulated claims separately from real JWT integration results. Never issue production tokens or disable production confirmation.
6. Seed distinct A/B rows, an incomplete B profile, an onboarded profile, active/inactive channels, active/hidden/deleted posts and comments, draft/published resources/events/opportunities, and user-owned notifications/bookmarks/tokens. Use unique run IDs for cleanup.

## Assertion protocol

For every case record identity, request, table/columns, expected visibility or mutation, actual status/body/row count, and database before/after state. SELECT denied by RLS often returns an empty set; UPDATE/DELETE may succeed with zero affected rows. Do not accept HTTP status alone as proof of denial. Request returned representations for positive mutations and confirm their persistence as the same user. Validate denied writes left rows unchanged with the setup connection.

Run the existing pgTAP structural assertions in the isolated database as a separate first step (with pgTAP installed), then execute this behavioral matrix. Roll back SQL transactions; remove API-created test users/rows after the run. Re-run from a fresh database to detect ordering dependencies.

## Failure and lifecycle scenarios

- Repeat selected reads/writes after logout, token expiry, refresh, account deletion, and role removal using real test JWTs. Document access-token lifetime/revocation semantics; logout does not necessarily invalidate an already issued JWT immediately.
- Switch from A to B in a fresh client and reuse A's row IDs to detect IDOR/cached-identity mistakes. Never share session storage between test clients.
- Simulate request interruption; retry with known identifiers, check duplicates and uniqueness, and verify partial failure does not broaden access.
- Inspect query plans/grants only as supporting evidence. A structural RLS flag is not proof that a policy's predicate is safe.

## Exit criteria and evidence

Every positive control succeeds, every forbidden operation is denied without a mutation or disclosure, and all discrepancies have recorded reproductions. Publish sanitized per-case results, migration versions, test project identifier, and cleanup confirmation. Treat policy gaps as blockers for affected features; propose additive migrations in a separate reviewed task. Do not weaken assertions to match an unsafe policy, rewrite historical migrations, or introduce an admin application.

## Milestone 1 executed identity coverage

A fresh isolated local Supabase instance applied all migrations and seed successfully. `tests/integration/student-identity.mjs` passed 40 real API/JWT assertions for identity persistence, privacy, consent, roles, verification and recovery. Existing structural pgTAP tests passed 10 assertions; `tests/rls/student_identity.sql` passed four behavioral assertions using simulated unverified claims. Test users were cleaned up. This establishes only the tested identity behavior; the remaining broad product matrix above is still a plan. See [the milestone report](milestone-1-report.md) for limits and configuration details.
